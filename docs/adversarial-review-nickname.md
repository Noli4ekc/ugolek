## CRITICAL

### NICK-01 · Слой 3 из редактора делает скрытое окно key — клавиатура/фокус уходят из поля посреди печати · CONFIRMED
**Где:** `Ugolek/Core/InboxEngine/InboxRunner.swift:223` (`window.makeKey()`), `:242` (`webView.becomeFirstResponder()`), `:111` (`makeKey()` в каждом `send`), `:201` (`teardown()` — **не вызывается ни разу во всём приложении**, grep по `Ugolek/` даёт только объявление); цепочка вызова: `FriendsView.swift:302` → `InboxRunner.fetchProfileNicknameAfterEnsure` (`InboxRunner.swift:185-188`) → `ensureLoaded` (`:49`) → `makeWindowAndWebView` (`:210`).

**Сценарий:**
1. Юзер открывает редактор друга, печатает юзернейм посимвольно. На каждое изменение — debounce 800 мс (`FriendsView.swift:275`).
2. Слой 1 на устройстве мёртв (заглушка 1462 байта, ~1–10 с с таймаутом). Слой 2 крутит до 25 с и на устройстве, вероятно, тоже пуст (NICK-07).
3. Через ~11–35 с после последнего нажатия каскад доходит до слоя 3: `ensureLoaded()` создаёт окно (1920×1080, alpha=0.01, x=-1930, `isHidden=false`) и вызывает `window.makeKey()`.
4. iOS переносит статус key-окна на невидимое окно: первое окно приложения теряет key, его first responder (TextField редактора) resign'ится — клавиатура складывается на середине ввода. Дополнительно `_ = webView.becomeFirstResponder()` явно уводит фокус в offscreen-webview.
5. После завершения фетча НИЧТО не возвращает key видимому окну: `teardown()` мёртвый код, повторного `makeKeyAndVisible` нет. Пока скрытое окно key, доставка тачей видимому UI зависит от маршрутизации UIApplication — как минимум клавиатура не вернётся сама.
6. Подвариант (проверено по коду): даже при НЕУДАЧЕ слоя 3 (`loginRequired`, `InboxRunner.swift:68` — throw ПОСЛЕ создания окна и загрузки login-страницы) окно уже создано и сделано key — фокус украден впустую.

**Severity:** CRITICAL — ломается основной UX редактора ровно в тот момент, ради которого фича существует. Часть про полную потерю тачей — SUSPECTED (зависит от маршрутизации событий между окнами одной сцены), часть про кражу клавиатуры — CONFIRMED кодовым путём без единого защитного гарда.

### NICK-02 · decodeUnicodeEscapes уничтожает суррогатные пары: эмодзи молча выпиливается из никнейма · CONFIRMED
**Где:** `Ugolek/Core/SessionStore/ProfileFetcher.swift:99-113`, ключевая строка `:106`: `if let code = UInt32(hex, radix: 16), let scalar = Unicode.Scalar(code)`.

**Механика:** эмодзи в JSON TikTok приходит как `\uD83D\uDE00`. Функция декодирует каждый `\uXXXX` отдельно. `Unicode.Scalar(0xD83D)` == **nil** (суррогатный диапазон D800…DFFF — невалидные скаляры в Swift) → обе половины пары выбрасываются, `out` их просто не получает. Ник «Anna😀» превращается в «Anna», чисто эмодзи-ник «🔥🔥» — в пустую строку → `nick.isEmpty ? nil : nick` (`:96`) → фолбэк считается несработавшим. Эмодзи в никнеймах TikTok — норма, а не экзотика.

**Компаундинг (хуже исходного дефекта):** в StreakEngine части B (`StreakEngine.swift:90`) `if fresh != friend.label { freshNick = fresh }` — испорченный ник ≠ хорошему сохранённому label → «свежий» признаётся обновлением → `AppStore.shared.update` (`:107`) ПЕРЕЗАПИСЫВАЕТ корректный label обрезанным. Ровно наоборот заявленной цели части B.

**Асимметрия с JS:** зеркало слоя 3 (`Resources/send.js:1058`) использует `String.fromCharCode(...)` — JS-строки UTF-16, две половины пары дают корректный астральный символ. То есть слой 3 сохраняет эмодзи, слой 1 — портит: результат каскада зависит от того, какой слой выжил.

Исполняемое доказательство: `Tests/AdversarialNicknameTests.swift`, `test_NICK_02_surrogatePairIsDroppedByDecodeUnicodeEscapes`.

**Severity:** CRITICAL (тихая порча данных, которая затем персистится частью B и автозаполнением).

### NICK-03 · nickTask не отменяется при закрытии редактора — каскад слоёв 2–3 стреляет после dismiss (включая ensureLoaded+makeKey посреди других экранов) · CONFIRMED
**Где:** `Ugolek/Screens/FriendsView.swift:261-321` — `handleChanged` создаёт `nickTask`; отмены нет нигде: ни в `save()` (`:324-338`), ни в «Отмена» (`dismiss()` без очистки), ни в «Удалить» (`:225-229`), ни в `.onDisappear` (его просто нет), ни в deinit-подобных точках.

**Сценарий:**
1. Юзер ввёл юзернейм, не дожидаясь ответа, нажал «Отмена»/«Сохранить» — шит закрылся.
2. `nickTask` продолжает спать debounce и идти по слоям: слой 1 (~1–10 с) → слой 2 (до 25 с, создаётся новый offscreen WKWebView, грузится страница) → слой 3 (`ensureLoaded()` → `window.makeKey()` — см. NICK-01).
3. Итог: юзер листает список друзей / другой экран — и в этот момент у него складывается клавиатура/крадётся фокус невидимым окном. Плюс впустую тратятся 2-3 сетевых запроса к TikTok от имени приложения.
4. Кооперативная отмена между слоями реализована правильно (`Task.isCancelled` на `:290/:301/:309`) — но отменять некому: единственный `cancel()` — `:262`, при СЛЕДУЮЩем нажатии клавиши, которого после dismiss не будет.

Записи в `label`/`nickState` из задачи закрытого view — меньшая часть проблемы; основное — побочные эффекты `ProfileWebFetcher.shared`/`InboxRunner.shared`.

**Severity:** CRITICAL (глобальная фокус-кража из модального контекста, усиливает NICK-01).

### NICK-04 · Защита ручных правок сломана порядком присваивания: устаревший автофилл никогда не обновляется · CONFIRMED
**Где:** `Ugolek/Screens/FriendsView.swift:310-316`:
```swift
autoFilledLabel = fresh                    // ← сначала ПЕРЕЗАПИСАЛИ
if label.isEmpty || label == autoFilledLabel {   // ← потом сравнили с НОВЫМ значением
    label = fresh
}
```
Замысел (`handle-verification-plan.md` §3.6, PLAN-10): перезаписывать метку, если она равна МОЁМУ ПРЕЖНЕМУ авто-значению. Реальность: старое значение `autoFilledLabel` затирается до сравнения, условие вырождается в `label == fresh`.

**Сценарий:**
1. Новый друг: автофилл нашёл «Old» → label=«Old», autoFilledLabel=«Old».
2. Профиль переименован в «New». Юзер переоткрывает редактор (label=«Old» из хранилища), двигает хендл (стерёл-вернул символ), каскад находит «New».
3. `autoFilledLabel=«New»`, условие `label(«Old») == «New»` = false → поле ОСТАЁТСЯ «Old», при этом плашка показывает «Имя распознано: New». Прямое противоречие UI↔поле; сохраняется снова «Old».
4. Единственный путь обновить автозначение — вручную стереть label полностью.

Зеркало-доказательство: `test_NICK_04_staleAutofillNeverRefreshes`.

**Severity:** HIGH — инвариант «метка актуальна», ради которого строился каскад, тихо не держится.

- `send.js:442` «Друг не найден: ни один кандидат не прошёл верификацию» — **это ровно деградация PLAN-07**: селектор панели сломался → КАЖДЫЙ друг с кандидатами проходит полный цикл открытий, потом часть B дёргает слой 1 → движок-fetch (`StreakEngine.swift:94`) → свежий WebView (`:97`), потом ОДИН retry-`send` (`:108`);

Сам факт отсутствия кэша и широты триггера — CONFIRMED; попадание под бан — SUSPECTED (не воспроизводимо локально).

### NICK-13 · Циклы опроса слоя 2 живут дольше своего запроса и могут будиться уже в ЧУЖОМ · CONFIRMED (интерливинг) / LOW (эффект)
**Где:** `ProfileWebFetcher.swift:61-73`. Каждый `didFinish` (их несколько в цепочке челлендж-редиректов) плодит свой `while self.continuation != nil` цикл. Двойной `finish` защищён continuation-nil (проверено: timeout/found/второй цикл — максимум один resume, см. «Отбито»). Но нет generation-токена: цикл цикла A уснул на `sleep(1.2)` в момент, когда запрос A закончился по таймауту и юзер тут же начал новый запрос B (continuation снова != nil) — проснувшись, он пуллит УЖЕ НОВЫЙ webView с новым handle (общее мутируемое состояние) и теоретически может завершить запрос B раньше его собственного цикла. Данных неверных это не даёт (handle общий, экстрактор тот же), но это нефункциональная гонка на общем состоянии без изоляции запросов.

## Отбито (атаки, не добившие подтверждения)

1. **Двойной `finish` слоя 2** (`ProfileWebFetcher.swift:46-59`): интерлевинг «timeout ↔ found ↔ второй цикл didFinish» — максимум один resume: единственная точка входа `finish` защищена `guard let cont = continuation else { return }` с немедленным `continuation = nil`. Второй претендент становится no-op. Подтверждено разбором всех трёх претендентов (timeoutTask, цикл из didFinish, повторный didFinish).
2. **Окно −300/+900 raw-поиска** (`ProfileFetcher.swift:87-89`): поиск сегмента ведётся СИММЕТРИЧНО вокруг `"uniqueId"`, а в реальной раскладке uniData/SIGI `nickname` стоит сразу после `uniqueId` (десятки символов). Атака «nickname дальше 300 ДО uniqueId» требует несуществующей раскладки; +900 вперёд покрывает с запасом. (Реальные баги окна — не в геометрии, а в регистре/кавычках: NICK-08/09.)
3. **Кооперативная отмена каскада редактора**: `Task.isCancelled` проверяется на каждой межслойной границе (`FriendsView.swift:290,301,309`); новое нажатие клавиши честно убивает предыдущую задачу до сетевых вызовов следующего слоя. Ломается только отсутствием отмены при dismiss (NICK-03) — сам механизм корректен.
4. **Single-flight `ensureLoaded`** (`InboxRunner.swift:50-52`): ранний return при уже загруженном движке и `throw .busy` при втором одновременном загрузчике — continuation первого не перезаписывается, вечных зависаний нет. Редакторский каскад во время активного прогона получает отказ, а не порчу.
5. **Параллельный `profileNickname` поверх активного `send`** (`InboxRunner.swift:171-181` vs `runJS`): ответ идёт через результат `evaluateJavaScript`, а не через bridge — `resultContinuation` не затрагивается; evaluateJavaScript сериализуются WebKit'ом; DOM-конфликта с `Ugolek.run` нет (разные функции). Остаточное — только CPU/лаги от 370 КБ ответа: LOW, не ломает.
6. **Гард `appearedHandle`** (`FriendsView.swift:269-272`): работает на финальном значении во всех разобранных вариантах (стёр-вернул то же, стёр не до конца и вернул, посимвольный набор). Цена промежуточных мусорных значений ограничена debounce 800 мс — это шум, а не поломка. Сравнение `clean == appearedHandle` консистентно, т.к. save() нормализует хендл теми же правилами (`:326-328`).
7. **Глубина рекурсии walk/findNickname**: вложенность uniData/SIGI — десятки уровней; стек JS и Swift переживает свободно (рекурсия хвостовая по дереву объекта, не по глубине строки). Атака «стек на 370 КБ JSON» не подтвердилась.
8. **Инъекция в JS-строки**: оба веб-фетчера фильтруют хендл до `[буквы|цифры|._]` перед интерполяцией (`ProfileWebFetcher.swift:20`, `InboxRunner.swift:173`) — закрыть кавычку/скобку в `const H='…'` или `'Ugolek.profileNickname(\'\(safe)\')'` невозможно.
9. **Жёсткие параметры retry** (`StreakEngine.swift:113-114` `isGroup:false, dryRun:false`): согласованы с гардом ветки (`!friend.isGroup, !dryRun` на `:84`) — недостижимы противоречивые комбинации.
