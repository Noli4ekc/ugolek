### PLAN-01. `CFG.scrollStep` не существует — сборщик кандидатов не покидает первый экран
- **План:217** — `nudgeScroll(target, CFG.scrollStep);` (блок `collectCandidates`, план:196–224).
- **Код: send.js:5–25** — `CFG` содержит `scrollStepMs:1200` (send.js:11) и `scrollMaxSteps:60` (send.js:12). Ключа `scrollStep` **нет**. Для сравнения: рабочий `findAndOpenChat` скроллит на `target.clientHeight * 0.7` (send.js:239), а не по ключу CFG.

**Сценарий воспроизведения:**
1. Реализация переносит код плана как есть (план озаглавлен «точный код для каждого файла»).
2. `CFG.scrollStep` → `undefined` → `nudgeScroll(target, undefined)`.
3. `nudgeScroll` (send.js:168–178): `step = Math.min(undefined, clientHeight*0.7)` = **NaN**; `target.scrollTop += NaN` — присваивание игнорируется (либо сбрасывает позицию, но не прокручивает вниз), `WheelEvent` уходит с `deltaY: NaN`.
4. Цикл честно крутит 61 итерацию (план:196, `<= scrollMaxSteps`) по одному и тому же первому экрану списка, спя `CFG.scrollStepMs` (этот ключ есть) — ~73 секунды впустую.
5. Друг ниже первого экрана → `exact=[]`, `fuzzy=[]` → ПРОХОД 2 по label → снова пусто → `throw 'Друг не найден в списке чатов'` (план:300).
6. Часть B подтягивает свежий label из профиля → повторный поиск → **тот же результат**.

**Масштаб:** массовая недоставка для всех, кто не в первом экране списка — то есть регрессия против текущего кода, который скроллит корректно.
**Severity:** CRITICAL. **Статус:** CONFIRMED (несуществующий символ + арифметика NaN).
**Тест:** `Tests/AdversarialHandlePlanTests.swift :: test_PLAN01_scrollStepUndefined_freezesCollectionAfterFirstScreen`.

### PLAN-03. Флаги mineToday/theirsToday накапливают ВСЮ историю окна — «сегодня» ни на что не влияет
- **План:258–275** (§3.1.C `lastMessageStatus`) — точный код:
  ```javascript
  if (today === null) break;
  if (isMine) mineToday = true; else theirsToday = true;
  ```
  Флаг ставится при **любом** вердикте, кроме `null`: и при `today===true`, и при `today===false`. Переменная `today` используется только как условие break (план:273). Собственно детекция «сегодня» — **вестигиална**: на флаги она не влияет вообще.
- Контекст замысла: план:101–113 («было ли СЕГОДНЯ моё?») и план:107–110 (оба флага → скип) — описание обещает today-гейт, «точный код» его не реализует.

**Сценарий воспроизведения (тред: вчера писал только я, сегодня никто):**
1. Дети контейнера (старые сверху): `[моё «Как дела?» + метка «Вчера»] [разделитель «Сегодня»] …` — сегодня сообщений нет.
2. Сканирование снизу вверх: разделитель «Сегодня» — регэксп `/вчера|дн|нед/i` ловит «**дн**» внутри «Сегодня» → `today=false` (≠null) → `theirsToday = true` (разделитель не «мой»).
3. Далее моё вчерашнее сообщение: «Вчера» → `today=false` → `mineToday = true`.
4. Итог: `mineToday && theirsToday` → `'maintained-today'` (план:277) → **СКИП друга с горящим, непродлённым стриком**, в истории «🔥 уже продлён сегодня».
5. Вариант хуже: вчерашнее сообщение с абсолютным временем «23:45» — якорь `/^\d{1,2}:\d{2}/` (план:267) классифицирует его как «сегодня».

**Масштаб:** любой живой тред, где обе стороны писали среди последних ≤10 распознаваемых узлов, даёт `'maintained-today'` → приложение молча перестаёт писать почти всем, рапортуя успех. Единственное, что спасает от тотального скипа, — сломанность эвристики направления (если все сообщения определяются как «его», статус вырождается в `'awaiting-reply'` и функция инертна). То есть Part D в написанном виде **либо вредит, либо не работает — третьего нет**.
**Severity:** CRITICAL. **Статус:** CONFIRMED (логика из собственного текста плана; конкретные узлы DOM — SUSPECTED, но на вывод не влияет).
**Тест:** `:: test_PLAN03_flagsIgnoreTodayVerdict_historyPollutesSkip`, `:: test_PLAN03_absoluteTimeFromYesterday_countedAsToday`, контрольный `:: test_PLAN03_control_cleanTodayBothThread_stillWorks`.

### PLAN-05. Регэкспы времени применяются к ПОЛНОМУ textContent — матчатся тексты сообщений
- **План:265–271**: `const t = (msg.textContent || '')` — затем четыре регэкспа по всей строке узла (имя автора + текст + метка времени).
- Подтверждаемые совпадения на русском:
  - «позвони **через 2 часа**» → `/(\d+)\s*(ч|час)/` → h=2 <24 → **today=true** у старого/чужого сообщения;
  - «зайду через 5 **минут**» → today=true;
  - «до встречи **днём**», «это было **однажды**», «уви**дн**мся сегодня», «**нед**авно» → `/вчера|дн|нед/i` → today=false;
  - разделитель «Сегодня» → today=false (см. PLAN-03);
  - «23:45» (вчерашняя абсолютная метка) → today=true.
- Эффект: вердикт управляет лишь «ставить флаг или прервать скан» (план:273–274). Ложный `true` продлевает скан и записывает флаг не той эпохе; ложный `false`/ранний `break` обрезает окно → статусы меняются на протиположные ('maintained-today'↔'awaiting-reply') → лишние отправки или скип живого долга.

**Сценарий:** их старое сообщение «набери через 2 часа» → `theirsToday=true` от вчерашней реплики; моё сегодняшнее ниже выпало из `slice(-10)` (план:252, см. миссию §4) → `mineToday=false` → `'awaiting-reply'` → повторная отправка при закрытом стрике.
**Severity:** HIGH. **Статус:** CONFIRMED на уровне регэкспов (зеркалимо); распределение узлов в DOM — SUSPECTED.
**Тест:** `:: test_PLAN05_timeRegex_matchesMessageBody_textVectors`, `:: test_PLAN05_windowOverflow_tenPlusMessagesToday_mineDropped_resendSpam`.

### PLAN-06. `resolveFresh()` коллапсирует тёзок: перебор кандидатов открывает одного и того же
- **План:303–338**: цикл считает, что `openChat(item)` открывает именно `item` (пусть и после `scrollIntoView` устаревшего узла, план:304).
- **Код: send.js:342–358** `resolveFresh(item)`: приоритет — `data-conv-id`; при его отсутствии — **фолбэк «первый подключённый узел с тем же nickname»** (send.js:350–356). Отсутствие conv-id — штатный случай: собственная диагностика кода печатает `нетConvId` (send.js:486).

**Сценарий (главный обещанный кейс плана — два друга «Нн», план:656–662):**
1. ПРОХОД 2 по label «нн»: `exact=[item1,item2]` (разные беседы, одинаковый ник).
2. У элементов нет `data-conv-id` → `resolveFresh(item2)` возвращает **item1**.
3. `openChat(item2)` фактически открывает item1; `chatOpenReady(item)` (send.js:311–315) сверяется тоже через `resolveFresh(item)` → «готово» подтверждается для item1.
4. Верификация: `actualHandle(twin1) !== wanted(twin2)` → closeChat → следующий «кандидат» → **снова item1** → снова не совпал.
5. `throw 'Друг не найден: ни один кандидат не подошёл по юзернейму'` (план:337) — хотя нужный чат был в списке.

Бонус-атака того же узла: кандидаты собраны как DOM-узлы на шаге N, открываются на шаге M (план:213–214 дедуп по identity — `includes(item)`); виртуализация пересоздаёт узлы → дубликаты кандидатов (один чат проверяется дважды) и отвязанные ссылки (`scrollIntoView` на detached — тихий no-op).
**Severity:** HIGH. **Статус:** CONFIRMED (логика resolveFresh зафиксирована кодом).
**Тест:** `:: test_PLAN06_resolveFresh_nicknameFallback_collapsesTwins`.

### PLAN-07. Null-верификация — тотальная регрессия доставки; первая `/@`-ссылка в панели может быть чужой
- **План:314–318**: `actualHandle === null` → пропуск кандидата; **план:587–591** (Риск 1) называет это компенсацией: «никакой отправки наугад не происходит».
- **План:233–235**: три селектора панели (`[data-e2e='chat-list'] ~ * [class*='MessageContent']`, `[class*='MessageThreadContainer']`, `[class*='dm-chat']`) — **ни один не встречается в текущем send.js**; код знает другие маркеры (`dm-new-chatbox`, `inbox-bar`, `nav-messages` — send.js:365–387). `data-e2e='chat-back'`-типа маркеры в коде не используются нигде.

**Сценарий А (регрессия):** сдвиг вёрстки/TikTok-апдейт → `handleFromOpenChat()` возвращает `null` для всех → каждый друг проходит путь «открыть правильный чат → не смог прочитать юзернейм → закрыть → …» → «Друг не найден» у **всех**. До фикса эти друзья получали сообщения. План легализует доставку 0% как «безопасность».
**Сценарий Б (чужой хендл):** `panel.querySelector("a[href*='/@']")` (план:237) берёт **первую** ссылку в панели — включая ссылки из тела сообщений (упоминание «@другой_юзер», шэр видео другого автора, которые рендерятся как `/@author`). Читается чужой хендл → несовпадение → **правильный чат пропускается** → друг «не найден».
**Severity:** HIGH. **Статус:** SUSPECTED (зависит от живого DOM), архитектурно — единственная точка истины «первый попавшийся `<a>`» подтверждена текстом плана.
**Тест:** `:: test_PLAN07_firstAtLinkInPanel_wins_overHeaderLink` + сценарный скетч `test_PLAN07_nullHandleForAllCandidates_totalDeliveryRegression_SKETCH`.

### PLAN-08. Два полных прохода скролла пробивают `sendTimeout=200с`; осиротевший результат вклеивается чужому другу
- **Код: InboxRunner.swift:46** — `sendTimeout = 200` (комментарий там же: «до 60×1200 мс × две попытки»).
- Арифметика плана: ПРОХОД 1 (юзернейм) + ПРОХОД 2 (label) — план:292–296; шаг цикла спит `CFG.scrollStepMs`=1200 мс × 61 итерация ≈ **73 с на проход**, итого ≈146 с **до открытия первого кандидата** (если друг не на первом экране). Плюс `waitForChatList` до 15 с (send.js:134–140), плюс ~4–6 с на каждого несовпавшего кандидата (план:305 sleep 500, openChat-раунды, closeChat 400).
- Оценка плана «+10–15 сек на retry» (**план:720**) занижена на порядок.

**Сценарий:**
1. Друг глубоко в списке / не найден: 73+73+кандидаты > 200 с → `runJS` таймаутит continuation (InboxRunner.swift:132–143), Swift получает «Превышено время ожидания (200 с)».
2. Эта ошибка **не содержит «не найден»** → Part B (план:428–429) не срабатывает именно для самых тяжёлых случаев.
3. JS-прогон продолжает жить в WebView; `resultContinuation` уже очищен → следующий друг стартует параллельно; когда старый прогон наконец постит `result`, `handle(_:)` (InboxRunner.swift:234–238) резюмит **чужой** continuation без проверки токена/username → другу B записывается результат друга A (в т.ч. `ok:false «Друг не найден»` → ложный Part B, или `ok:true` → друг B помечен продлённым, не получив ничего).
4. Два одновременных прогона кликают один DOM — взаимные закрытия панелей, отправки в чужой открытый чат.

**Severity:** HIGH. **Статус:** CONFIRMED (арифметика + отсутствие токена в `handle(result)`).
**Тест:** `:: test_PLAN08_scanBudget_exceeds200s_and_orphanResultCrossContamination`.
